Bug report · DSX for Applications · ICAP

ICAP returns 500 "Classification Failed" for every malicious file in disconnected deployments when the request has no X-Client-IP header

Product / buildDSX/A Scanner 4.3.0.2348 (DeepInstinctICAP/4.3.0.2348p)
SeverityHigh: malicious ICAP detections return a server error and are not logged
AffectsDisconnected (air-gapped) ICAP, RESPMOD and REQMOD
WorkaroundClient sends X-Client-IP

Summary

In a disconnected deployment, the ICAP service answers every malicious verdict with ICAP/1.0 500 Internal Server Error, plus an encapsulated HTTP/1.1 500 and X-Blocked-Reason: Classification Failed, whenever the ICAP request has no X-Client-IP header. The file is detected, but the response is a server error, no verdict is written to the scanner log, and the end user gets an HTTP 500 instead of the block page.

Clean files are unaffected. The same image in a connected deployment returns the correct 200 + HTTP/1.1 403 block response. When the client sends X-Client-IP, the disconnected deployment behaves correctly too.

The root cause is a missing-header default in pyicap.py that sets the client IP to the integer 78. That integer crashes the legacy block-page path, which only disconnected deployments use because their default policy package has no P_006 block page. Details are in the root-cause section below.

Root cause

1. Missing X-Client-IP becomes the integer 78

/bin/perimeter/icap_server/pyicap.py, line 479:

self.client_ip = self.headers.get(b'x-client-ip', b'No X-Client-IP header')[0]

Header values are stored as lists, so [0] is meant to take the first value. The fallback for a missing header is a bytes string rather than a list, so [0] returns its first byte: ord('N') == 78. ctx.request_src_ip is then an int. This affects every deployment and shows up as X-Client-IP: 78 in the response headers and block pages.

2. The legacy block page cannot handle an int

/bin/perimeter/icap_server/icap_result_handler.py, line 185 picks the block page:

body = self.get_policy_block_page() or self.get_legacy_block_page()

get_policy_block_page() renders policy file P_006 and passes every value through normalize_value(), which copes with the int. get_legacy_block_page() (line 66) does a raw bytes replace:

body = body.replace(b"SOURCE_IP", self.ctx.request_src_ip)   # int -> TypeError

That raises TypeError: a bytes-like object is required, not 'int'. The exception handler in di_icap_server.py (around line 565) then turns the response into ICAP 500 "Classification Failed".

3. Why only disconnected deployments fail

The policy from a connected console includes P_006 (the customizable block page), so the safe policy path is used. The disconnected default policy package has no P_006: compared with the connected file set, it lacks P_006 and DP_001. So get_policy_block_page() returns None, the legacy path runs, and every malicious verdict fails. Clean files never build a block page, so they're unaffected.

Impact

  • Proxy behavior is undefined. Many ICAP clients treat a 500 as a scanner failure and either fail open (deliver the malicious file) or fail closed (block all traffic), depending on their settings.
  • End users see HTTP 500 on blocked uploads and downloads instead of the 403 block page.
  • Contradictory headers: the response carries both X-Blocked-Reason: Infected and Classification Failed.
  • No audit trail: no "verdict": "Malicious" entry is logged, so malicious ICAP detections are invisible in the scanner logs. In disconnected mode there's no console to fall back on.
  • Wrong data in both modes: X-Client-IP: 78 appears in response headers, and in the client-IP field of the block page.

Workaround: configure the ICAP client to send X-Client-IP. Most production proxies do so by default; in Squid, set adaptation_send_client_ip on. With the header present, the disconnected deployment returns the correct 200 / 403 response and logs the verdict.

Suggested fix

  1. pyicap.py: make the default a list, so [0] returns bytes: 
    self.client_ip = self.headers.get(b'x-client-ip', [b'-'])[0]
  2. icap_result_handler.get_legacy_block_page(): normalize values before the replace, as the policy page does: 
    body = body.replace(b"SOURCE_IP", self.normalize_value(self.ctx.request_src_ip).encode("utf-8"))
  3. Include P_006 in the disconnected default policy package, so air-gapped customers get the same customizable block page as connected ones.
  4. Add a regression test: a malicious RESPMOD and REQMOD with no X-Client-IP, against both the policy and the legacy block-page paths.

Additional defects found in the same build (load testing, Oct 20)

These were found while reproducing a customer ICAP load-test ticket on the connected 4.3.0.2348 build (images built Oct 18), with ICAP over TLS and the customer's own test client. Each is independent of the X-Client-IP bug above.

2. ICAP forks one process per connection and exceeds the platform's per-pod process limit

Severity: High. Under connection churn, the ICAP pod returns ICAP 500s and drops connections instead of throttling or queueing.

  • Trigger: 100 concurrent clients, each opening a new TCP + TLS connection per file (the customer's aggressive_tls_socketing: true), against one ICAP pod.
  • Mechanism: di_icap_server.py uses socketserver.ForkingMixIn (ForkingWithAtomicMixIn, max_children = 5000), so every connection forks. The classifier forks again (ClassifierPython.cpp:268). The pod reached about 4,050 processes within seconds. OpenShift's default podPidsLimit is 4096, so further forks failed with EAGAIN.
  • Symptoms: Failed to fork, errno: 11, BlockingIOError: [Errno 11] Resource temporarily unavailable, and Classifier failed handling file. Error: Resource temporarily unavailable, giving ICAP 500 "Classification Failed". Clients saw TCP resets and broken pipes. In a 120 s run: 107 × ICAP 500, 301 broken pipes and 180 resets. Reputation lookups also failed with curl result 6 (could not resolve host) while processes were exhausted.
  • Hidden by CPU limits: with the default 4-core limit the pod saturates CPU first. Requests then queue for up to 56 s and some hit client read timeouts. Raising the limit to 8 cores exposed the process exhaustion.
  • Mitigations that worked: three replicas (no errors, 206 files/s, peak 2,724 processes per pod), or clients reusing connections.

Suggested fix: derive the child cap from the container's effective process limit (cgroup pids.max of the pod), and make it well below it. When the cap is reached, queue the request or answer ICAP 503 instead of failing mid-request. Consider a bounded worker pool, or threads for TLS handling, instead of fork-per-connection, and reap exited children promptly. Document per-pod concurrency sizing and recommend HPA for ICAP.

3. The REST liveness probe fails when the default protected application has token binding

Severity: High. The REST pod restarts in a loop, and scanning stops during each restart.

  • Trigger: in the console, the scanner's default protected application has a protected-application token configured.
  • Mechanism: Utils/check_pod_liveness.py test_rest() posts a test file to localhost:5000/scan/binary/v2. It sends AUTH when an auth token is set, plus Test-File: dpa-test, but no protected_entity and no Protected-Application-Token. The request falls to the token-bound default entity and gets 401 (bad res in test_rest: <Response [401]>), so the kubelet kills the dpa container.
  • Observed: 96 restarts over about 4 days; the loop stopped as soon as the token was removed from the default protected application.

Suggested fix: exempt the internal health check from token binding (it already sends a Test-File marker), or give the probe a dedicated health endpoint that doesn't go through protected-application checks.

4. Cloud reputation lookups time out under moderate load

Severity: Medium. Under load, scans silently go without the reputation result.

  • Observed: KnownThreats.cpp:432: Failed to get an answer from DCloud, made 3 attempts using this hash … last error: REQUEST_CURLE_TIMEOUT for most scans of two ELF samples, at 94–206 files/s: 1,550 to 3,328 failures per 120 s run, with persistent and per-file TLS alike, on one pod or three.
  • Not load-free behavior: the same files scanned singly return in 0.10–0.15 s with no lookup errors.
  • Impact: verdicts are still returned, but without the reputation result; each failed lookup also adds latency.

Suggested fix: cache lookups per hash and collapse concurrent lookups for the same hash into one request. Review the curl timeout and retry budget under concurrency, and expose a metric or log summary for skipped reputation checks.
