Recreating the OpenShift/GCP DSX/A Environment

This runbook describes how to recreate the DSX/A environment on Red Hat OpenShift running on Google Cloud Platform (GCP), including the DSX/A REST and ICAP scanners. It covers:

  1. Creating and preparing the GCP project
  2. Creating the OpenShift cluster
  3. Creating the OpenShift project
  4. Choosing an image source and configuring registry access
  5. Verifying storage
  6. Creating DSX/A Helm values
  7. Deploying DSX/A (REST and ICAP)
  8. Verifying and testing the deployment
  9. Exposing the scanners, TLS and DNS
  10. Administrator access (oc, k9s, web console)
  11. Troubleshooting
  12. Cleanup

The repository contains the DSX/A Helm chart. It does not yet contain complete Terraform or Ansible automation for creating the GCP project, IAM, networking, DNS and the OpenShift cluster.

What changed in this revision (October 2026, DSX/A 4.3.0.2348 on OCP 4.22)

  • Added a single-node (SNO), internal-only cluster variant and the lab's actual values (reference table below).
  • Section 4: loading the 4.3 images from the console download into your own registry (the OpenShift internal registry in the lab), so no Deep Instinct registry credentials are needed.
  • Section 6: where to get the registration token, the hostname format for management_server_url, and resource sizing for small clusters.
  • Section 7: deploying ICAP as a separate pod.
  • Section 8: the correct REST, scan-by-path and ICAP endpoints, with test commands and expected results. Note that scan-by-path uses GET. Also REST token auth, which uses an AUTH header, not AUTH_TOKEN.
  • Section 9: exposing the REST scanner outside the VPC, restricted to allow-listed IPs.
  • New sections 10 and 11: laptop access through an IAP/SOCKS tunnel, and the issues hit during this build.
  • Section 12: cleaning up an orphaned cluster whose install directory has been lost.

Architecture choice

This runbook assumes self-managed OpenShift Container Platform on GCP, installed with installer-provisioned infrastructure (IPI).

The chart value GCP-OCP means OpenShift running on GCP, which is not the same as GKE. In this mode the chart creates an OpenShift Route for the REST service and a GCP Persistent Disk storage class for MongoDB.

Google Cloud also offers managed OpenShift Dedicated. Creating a managed cluster works differently, but the project, namespace, registry and Helm steps that follow cluster creation are similar.

Prerequisites

Obtain or install the following before you begin:

  • A Google Cloud account with permission to create projects, IAM resources, networks, DNS records and Compute Engine resources
  • A GCP billing account
  • A Red Hat OpenShift subscription or Google Cloud Marketplace entitlement
  • An OpenShift pull secret
  • The gcloud, oc and openshift-install CLIs, and Helm 3 (the lab used OCP 4.22.0 tools and Helm v3.19.0)
  • A DNS domain that can be delegated to the OpenShift cluster
  • Access to the DSX/A management console, to get the management-server hostname, the registration token, the scanner ID and the Helm chart
  • Optional: Artifact Registry credentials for us-docker.pkg.dev/di-dsx-external-artifacts. Not needed if you load the images from the console download into your own registry (section 4).
  • Optional, on your laptop: kubectl and k9s for direct cluster access (section 10)

1. Create the GCP project

Set the project and billing variables, replacing all placeholder values:

export GCP_PROJECT="my-dsxa-ocp"
export GCP_BILLING_ACCOUNT="000000-000000-000000"
export GCP_REGION="us-east1"
export GCP_ZONE="us-east1-b"

gcloud projects create "$GCP_PROJECT"
gcloud billing projects link "$GCP_PROJECT" --billing-account="$GCP_BILLING_ACCOUNT"
gcloud config set project "$GCP_PROJECT"

Enable the APIs needed for the OpenShift installation and DSX/A:

gcloud services enable \
  compute.googleapis.com \
  cloudresourcemanager.googleapis.com \
  dns.googleapis.com \
  iam.googleapis.com \
  iamcredentials.googleapis.com \
  serviceusage.googleapis.com \
  artifactregistry.googleapis.com \
  storage.googleapis.com \
  iap.googleapis.com

GCP service account

Create a service account for the OpenShift installer:

gcloud iam service-accounts create openshift-installer \
  --display-name="OpenShift installer" --project="$GCP_PROJECT"
export INSTALLER_SA="openshift-installer@${GCP_PROJECT}.iam.gserviceaccount.com"

Unless your organization has defined custom roles, the installer needs broad permissions. Red Hat documents the required roles in the GCP installation guide. For a temporary lab, an administrator can grant the service account the required project-level access. For production, use the least-privilege roles approved by the cloud-security team.

Create a JSON key only if your installation method requires one:

gcloud iam service-accounts keys create openshift-installer.json \
  --iam-account="$INSTALLER_SA" --project="$GCP_PROJECT"
export GOOGLE_APPLICATION_CREDENTIALS="$PWD/openshift-installer.json"

Protect this file, and delete it after the installation if you no longer need it.

Network and admin VM (internal-cluster variant)

The lab cluster runs in an existing VPC and is published internally. All installer, oc and Helm work runs from a small admin VM in the same VPC. SSH to it goes through IAP, because direct SSH on port 22 is firewalled:

gcloud compute ssh ocp-sno-admin --zone us-east1-b --tunnel-through-iap

The consider installing NumPy warning that IAP prints is harmless.

2. Create the OpenShift cluster

On the admin VM, download the installer and client for the target release:

mkdir -p ~/ocp422 && cd ~/ocp422
curl -fLO https://mirror.openshift.com/pub/openshift-v4/x86_64/clients/ocp/4.22.0/openshift-install-linux.tar.gz
curl -fLO https://mirror.openshift.com/pub/openshift-v4/x86_64/clients/ocp/4.22.0/openshift-client-linux.tar.gz
tar -xzf openshift-install-linux.tar.gz && tar -xzf openshift-client-linux.tar.gz
chmod +x openshift-install oc kubectl
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519 -N ''

Create a working directory and generate the installer configuration:

mkdir -p "$HOME/ocp-install/dsxa-gcp" && cd "$HOME/ocp-install/dsxa-gcp"
openshift-install create install-config

Provide values similar to these. The standard HA layout:

apiVersion: v1
baseDomain: ocp.example.com
metadata:
  name: dsxa
platform:
  gcp:
    projectID: my-dsxa-ocp
    region: us-east1
controlPlane:
  replicas: 3
compute:
  - name: worker
    replicas: 3
pullSecret: '<red-hat-pull-secret-json>'
sshKey: '<ssh-public-key>'

The lab used a single-node, internal-only layout in an existing VPC. The installer deletes install-config.yaml, so the file below is reconstructed from the running cluster; check the values before reusing them.

apiVersion: v1
baseDomain: ocp-test.deepinstinctweb.com
metadata:
  name: dsxa422
controlPlane:
  name: master
  replicas: 1                 # single node: control plane and workloads on one VM
  platform:
    gcp:
      type: n2-standard-8     # 8 vCPU / 32 GB
compute:
  - name: worker
    replicas: 0
platform:
  gcp:
    projectID: se-project-388112
    region: us-east1
    network: ocp-sno-net
    controlPlaneSubnet: ocp-sno-us-east1
    computeSubnet: ocp-sno-us-east1
publish: Internal             # API and ingress on internal load balancers only
pullSecret: '<red-hat-pull-secret-json>'
sshKey: '<ssh-public-key>'

Single node leaves little room for DSX/A. 8 vCPU gives 7.5 allocatable cores, and OpenShift reserves about 3 of them. The DSX/A default resource requests don't fit without the sizing in section 6. Use n2-standard-16 if you want to keep the chart defaults.

Before installing, review the generated install-config.yaml and confirm:

  • The GCP project and region are correct.
  • The cluster name is correct and isn't already used in the project.
  • The base DNS domain is delegated correctly.
  • The machine types and replica counts meet the intended capacity.
  • The VPC and subnets are correct, if you're using an existing network.
  • Private-cluster (publish: Internal), proxy or restricted-network settings are configured if required.

Keep a copy of the file, because the installer consumes it:

cp install-config.yaml ../install-config.dsxa.keep

Install the cluster:

openshift-install create cluster --dir "$HOME/ocp-install/dsxa-gcp" --log-level=info

# If the session drops, re-attach with:
openshift-install wait-for bootstrap-complete --dir "$HOME/ocp-install/dsxa-gcp"
openshift-install wait-for install-complete  --dir "$HOME/ocp-install/dsxa-gcp"

Save the administrator password (auth/kubeadmin-password) and the API URL. Don't delete the installation directory; you need it for troubleshooting and for destroying the cluster.

Use one installation directory per cluster, and never reuse one for a retry. The directory's metadata.json is the only record of which cluster it owns. In the lab, retries led to a second, orphaned cluster running alongside the real one, with a confusingly similar name. Before running destroy on any directory, confirm its infra ID:

grep -o '"infraID":"[^"]*"' "$HOME/ocp-install/dsxa-gcp/metadata.json"

Configure the local OpenShift client:

export KUBECONFIG="$HOME/ocp-install/dsxa-gcp/auth/kubeconfig"
oc get infrastructure cluster -o jsonpath='{.status.infrastructureName}{"\n"}'   # should match the infraID
oc get nodes
oc get clusterversion
oc get co

Wait until every cluster operator reports Available=True, Progressing=False and Degraded=False.

3. Create the OpenShift project

Create a dedicated project for DSX/A. The lab named it after the release, dsxa-430, so that several versions can sit side by side.

oc new-project dsxa \
  --display-name="DSX/A Scanner" \
  --description="Deep Instinct DSX/A scanner environment"
oc get project dsxa

Don't grant additional security-context permissions. The 4.3.0.2348 chart sets no pod or container security context, and its pods run under the default restricted-v2 SCC. MongoDB requests a privileged container only when cloud_provider is LOCAL-OCP. The sysctl: permission denied on key "kernel.core_pattern" line at pod start-up is harmless.

4. Choose an image source and configure registry access

Option A: Your own registry, from the console download (used in the lab)

In the console, Settings → Deployment → Application Security, select version 4.3.0.2348 and choose Download Container Image File. The package (dpa-rocky9-4.3.0.2348.tgz, about 770 MB) holds three image archives:

Archive in the packageValues keyPush as
dpa-rocky9-4.3.0.2348-base.tgzimages.dpa_repositorydpa-rocky9:4.3.0.2348
rsync-dpa-4.3.0.2348.tgzimages.conf_repositoryrsync-dpa:4.3.0.2348
mongo-dpa-4.3.0.2348.tgzimages.mongo_repositorymongo-dpa:4.3.0.2348

Push them to any registry the cluster can pull from. The lab used the OpenShift internal registry in the scanner's own namespace, so no pull secret is needed:

# one-time: expose the internal registry (on a publish: Internal cluster the route is VPC-only)
oc patch configs.imageregistry.operator.openshift.io/cluster --type merge -p '{"spec":{"defaultRoute":true}}'
oc create sa image-pusher -n dsxa
oc policy add-role-to-user registry-editor -z image-pusher -n dsxa
REG=$(oc get route default-route -n openshift-image-registry -o jsonpath='{.spec.host}')
TOK=$(oc create token image-pusher -n dsxa --duration=2h)

tar -xzf dpa-rocky9-4.3.0.2348.tgz
for i in dpa-rocky9:dpa-rocky9-4.3.0.2348-base rsync-dpa:rsync-dpa-4.3.0.2348 mongo-dpa:mongo-dpa-4.3.0.2348; do
  skopeo copy --dest-tls-verify=false --dest-creds "image-pusher:$TOK" \
    docker-archive:${i#*:}.tgz docker://$REG/dsxa/${i%%:*}:4.3.0.2348
done
oc get imagestreams -n dsxa

Then set global.image_tag: "4.3.0.2348", global.registry.enabled: false, and point the three images.*_repository keys at image-registry.openshift-image-registry.svc:5000/dsxa/<name>.

On a single-node cluster, enabling the registry route triggers a kube-apiserver rollout: the API is unavailable for a few minutes. Pods in another namespace can use these images after oc policy add-role-to-user system:image-puller system:serviceaccount:<ns>:default -n dsxa.

Option B: Deep Instinct Artifact Registry

The chart's defaults point to us-docker.pkg.dev/di-dsx-external-artifacts/dsx-docker/. This registry rejects anonymous pulls and ordinary Deep Instinct GCP accounts (401/403), so you need a service-account JSON key authorized to pull from it. Create an image-pull secret:

oc create secret docker-registry deepinstinct-registry \
  --docker-server=us-docker.pkg.dev \
  --docker-username=_json_key \
  --docker-password="$(cat gcp-registry-reader.json)" \
  --docker-email="platform@example.com" \
  --namespace=dsxa

Then set registry.enabled: true, createSecret: false and secret_name: deepinstinct-registry. Don't put the JSON key in a committed values file.

5. Verify storage

oc get csidrivers
oc get storageclass

For GCP-OCP the chart creates its own GCP Persistent Disk CSI storage class for the MongoDB volume (di-ssd-<namespace>-<scanner_id>, 20Gi by default). Confirm that pd.csi.storage.gke.io is listed. The 4.3 chart can use an existing class instead, through mongo.storageClassName.

Scan-by-path is optional. To enable it, configure an NFS or SMB share. The lab used:

rest:
  share:
    allow_scan_by_path: true
    protocol: nfs
    server: 10.50.0.2
    path: /srv/dpa-scan
    size: 300Gi

6. Create DSX/A Helm values

Get the chart and token from the management console

  1. Go to Settings → Deployment → Application Security (/app/#/settings/deployment-resources/dpa/connected).
  2. Select the version (4.3.0.2348) and the scanner.
  3. Copy the Registration Token. It's a 36-character UUID (xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx), and it belongs to the scanner selected in step 2.
  4. Under Cluster, choose Download Helm Chart (dpa-helm-4.3.0.2348.tgz). Its Chart.yaml says version 4.3.0; the image build is set with global.image_tag.

Values file

Create an environment-specific values file outside the chart, or in a secured deployment repository. Don't edit the chart's own values.yaml. This is the working lab file:

global:
  cloud_provider: GCP-OCP
  management_server_url: cs-test744.customers.deepinstinctweb.com   # hostname only; the pod adds the apiv2- prefix itself
  registration_token: "<registration-token>"
  scanner_id: 1
  image_tag: "4.3.0.2348"
  registry:
    enabled: false                       # Option A (own registry, same namespace)

images:
  dpa_repository:   image-registry.openshift-image-registry.svc:5000/dsxa/dpa-rocky9
  conf_repository:  image-registry.openshift-image-registry.svc:5000/dsxa/rsync-dpa
  mongo_repository: image-registry.openshift-image-registry.svc:5000/dsxa/mongo-dpa

rest:
  deployment_enabled: true
  service:
    deploy_ingress: true                 # OpenShift Route
    type: ClusterIP                      # LoadBalancer to expose it outside the VPC (section 9)
  resources:
    requests: {cpu: "250m", memory: "2Gi"}
    limits:   {cpu: "4",    memory: "16Gi"}

icap:
  deployment_enabled: true               # separate icap-<id> pod
  service: {type: ClusterIP, port: 1344}
  resources:
    requests: {cpu: "500m", memory: "2Gi"}
    limits:   {cpu: "4",    memory: "16Gi"}

config:
  resources:
    requests: {cpu: "100m", memory: "1Gi"}
    limits:   {cpu: "1",    memory: "2Gi"}

mongo:
  resources:
    requests: {cpu: "100m", memory: "512Mi"}
    limits:   {cpu: "1",    memory: "1Gi"}

Sizing: the chart defaults request 2 CPU / 8Gi each for REST and ICAP, and every config, rest and icap pod also has a sync sidecar fixed at 1 CPU. On a cluster with spare capacity, remove the resources blocks to use the defaults. The reduced requests above fit a single 8-vCPU node, and the limits still allow bursting.

Scanner ID: resource names include it (rest-1, route-rest-1-<ns>, and so on), so changing it renames everything.

The chart path in the repository is dist/dsxa_deployment/dpa/dpa-chart; in the downloaded archive it's dpa/dpa-chart. The base configuration is documented in its values.yaml.

7. Deploy DSX/A

Render the chart first and review the result, then install it:

export DSXA_NAMESPACE="dsxa"
export DSXA_CHART="$PWD/dist/dsxa_deployment/dpa/dpa-chart"

helm template dsxa "$DSXA_CHART" -n "$DSXA_NAMESPACE" -f values-gcp-ocp.yaml > rendered.yaml

helm upgrade --install dsxa "$DSXA_CHART" \
  --namespace "$DSXA_NAMESPACE" --create-namespace \
  -f values-gcp-ocp.yaml --wait --timeout 15m

If the current directory isn't the repository root, use an absolute path for DSXA_CHART.

With icap.deployment_enabled: true, ICAP runs as its own deployment, icap-<scanner_id>, with its own service on port 1344. REST and ICAP share the config and mongo pods. To add ICAP to an existing release, set the flag and run the same helm upgrade.

Single node: rolling updates can stall. A replacement pod needs CPU that its predecessor still holds, so it stays Pending with Insufficient cpu. Delete the old pod, or scale the deployment to 0 and back to 1. Expect a short interruption.

8. Verify and test the deployment

helm status dsxa -n dsxa
oc get pods,deployments,services,routes,pvc -n dsxa
oc rollout status deployment -n dsxa --timeout=15m

Confirm that the config pod registered with the management server:

oc logs -n dsxa deployment/config-1 -c dpa --tail=20
#   Registration succeeded
#   Updates downloaded successfully ...
oc logs -n dsxa deployment/rest-1 -c dpa --tail=20
#   Classifier initialized. Result: true

Until registration succeeds, REST answers every scan with "reason": "SYSTEM_INITIALIZING", and the sync sidecars log failed to connect to config-1 ... Connection refused. Both are expected at that stage. The scanner should also show as connected in the management console.

REST

The REST endpoint is the Route hostname (oc get route -n dsxa); use it as the DSX/A endpoint for DSX-Connect. The scan path is /scan/binary/v2; a bare /scan returns 404.

curl -X POST http://<route-host-or-ip>/scan/binary/v2 \
  -H 'Content-Type: application/octet-stream' -H 'X-File-Name: ls' \
  --data-binary @/bin/ls
# {"verdict":"Benign", ...}

An EICAR test file returns "verdict":"Malicious", "file_type":"EICARType". The guide also documents /scan/base64/v2, /scan/by_hash and /scan/by_path.

REST token authentication (optional)

By default REST accepts any request. To require a static token (16 to 512 bytes), keep it in a secret, not in the values file:

python3 -c "import secrets;print(secrets.token_hex(16),end='')" > rest-auth-token.txt   # chmod 600
kubectl create secret generic auth-token -n dsxa --from-file=AUTH_TOKEN=rest-auth-token.txt
rest:
  auth_token_secret: auth-token     # note: under rest:, not rest.secure
  auth_token_key: AUTH_TOKEN
  # or inline (not recommended): auth_token: "<token>"

Run helm upgrade; only the REST pod restarts. Clients then send the token in a header named AUTH:

curl -X POST http://<route-host-or-ip>/scan/binary/v2 \
  -H 'Content-Type: application/octet-stream' -H "AUTH: $TOKEN" --data-binary @/bin/ls

The header is AUTH, not AUTH_TOKEN. The 4.1 and 4.2 guides say AUTH_TOKEN (the 4.3 guide is correct), but 4.3.0.2348 rejects that, along with Auth-Token, X-Auth-Token and Authorization: Bearer, returning 401 even with the correct token. The pod's own health check (check_pod_liveness.py) sends AUTH.

Request (token enabled)Result
No header, or a wrong token401 {"error":"401 Unauthorized: Invalid authorization"}
AUTH: <token> on /scan/binary/v2200, with normal verdicts (Benign / Malicious)
AUTH: <token> on /scan/by_path and /result/by_path/<guid>200; both endpoints require the token

The token applies to REST only; ICAP is unaffected. To turn it off, remove the two keys and upgrade again.

Scan by path (REST, asynchronous)

Requires rest.share.allow_scan_by_path: true (section 5). The share is mounted in the REST pod at rest.share.scan_path, which defaults to /scan_files. Check the mount and place a test file on it:

kubectl exec -n dsxa deploy/rest-1 -c dpa -- sh -c "mount | grep scan_files"
# 10.50.0.2:/srv/dpa-scan on /scan_files type nfs4 (rw,...)
kubectl exec -n dsxa deploy/rest-1 -c dpa -- sh -c "mkdir -p /scan_files/sbp-test && cp /usr/bin/bash /scan_files/sbp-test/bash"

Submit the scan, then fetch the verdict with the returned scan_guid. The Stream-Path header is the path as the pod sees it (under /scan_files), not the path on the NFS server.

curl -X GET http://<route-host-or-ip>/scan/by_path \
  -H 'Content-Type: application/octet-stream' \
  -H 'Stream-Path: /scan_files/sbp-test/bash' \
  -H 'X-Custom-Metadata: sbp-test'
# {"scan_guid":"c6f13fd5...","verdict":"Scanning","verdict_details":{"event_description":"Stream scanning in progress"}}

curl http://<route-host-or-ip>/result/by_path/<scan_guid>
# {"verdict":"Benign","file_info":{"file_type":"ELF64FileType","file_size_in_bytes":1389024,...}}

Use GET for /scan/by_path. POST returns 405 Method Not Allowed, even though the guide's text describes it as a POST request; its curl example uses -X GET. Until the verdict is ready, /result/by_path keeps returning "Scanning". Small files finish within seconds; extraction can take up to 25 minutes per GB.

Lab results: EICAR on the share came back Malicious (EICARType), and a 1.4 MB ELF binary came back Benign.

ICAP

The ICAP service URLs are icap://<host>:1344/response (RESPMOD) and /request (REQMOD). Any other path, including /respmod and /, returns ICAP/1.0 404; the 4.2 guide doesn't list these paths. To test from inside the cluster:

oc exec -i -n dsxa deploy/rest-1 -c dpa -- python3 - <<'EOF'
import socket
def icap(req):
    s=socket.create_connection(("icap-1",1344),timeout=60); s.sendall(req); out=b""
    while True:
        d=s.recv(65536)
        if not d: break
        out+=d
        if b"\r\n\r\n" in out: break
    s.close(); return out.decode(errors="replace")
print(icap(b"OPTIONS icap://icap-1:1344/response ICAP/1.0\r\nHost: icap-1\r\n\r\n"))
body=b"hello dsx\n"
rh=b"HTTP/1.1 200 OK\r\nContent-Type: application/octet-stream\r\nContent-Length: %d\r\n\r\n"%len(body)
req=(b"RESPMOD icap://icap-1:1344/response ICAP/1.0\r\nHost: icap-1\r\nX-File-Name: clean.txt\r\nAllow: 204\r\n"
     b"Encapsulated: res-hdr=0, res-body=%d\r\n\r\n"%len(rh)+rh+b"%x\r\n"%len(body)+body+b"\r\n0\r\n\r\n")
print(icap(req))
EOF

9. Exposing the scanners, TLS and DNS

Route (default)

The chart creates an OpenShift Route for REST. With edge termination enabled, TLS terminates at the OpenShift router:

rest:
  secure:
    enable_ssl_on_ocp_route: true

The Route is only as reachable as the cluster's ingress. On a publish: Internal cluster, it resolves and answers only inside the VPC.

External load balancer for REST, IP-restricted (used in the lab)

To reach REST from outside the VPC without exposing the rest of the cluster, set rest.service.type: LoadBalancer and upgrade. GCP then creates an external TCP load balancer for the REST service only. The chart has no setting for allowed source IPs, so restrict the service straight after the upgrade. Kubernetes turns loadBalancerSourceRanges into the GCP firewall rule k8s-fw-<lb>.

helm upgrade dsxa "$DSXA_CHART" -n dsxa -f values-gcp-ocp.yaml
oc patch svc rest-1 -n dsxa --type merge \
  -p '{"spec":{"loadBalancerSourceRanges":["<allowed-ip>/32"]}}'
oc get svc rest-1 -n dsxa                       # EXTERNAL-IP
gcloud compute firewall-rules list --filter='name~k8s-fw' \
  --format='table(name,sourceRanges.list(),allowed[].map().firewall_rule().list())'
  • Normal helm upgrades keep the patch, but you must reapply it after an uninstall and reinstall. The patch replaces the whole list, so include every allowed IP.
  • This serves plain HTTP on port 80. Add TLS (rest.secure and the rest_ssl_secret optional template) before scanning real files over the internet.
  • ICAP can be exposed the same way: icap.service.type: LoadBalancer, then the same patch on icap-1.

Custom hostname and certificates

For a custom hostname, add a DNS record pointing at the router or load balancer IP. If you need a custom certificate, follow the organization's approved OpenShift TLS process; don't commit certificate or private-key material to the repository.

10. Administrator access (oc, k9s, web console)

On an internal cluster the API and console can be reached only from the VPC. From a laptop, use a SOCKS tunnel through the admin VM; nothing is exposed publicly.

# 1. Copy the kubeconfig to the laptop
gcloud compute scp ocp-sno-admin:ocp422/install-dsxa422-r4/auth/kubeconfig ~/.kube/dsxa422.kubeconfig \
  --zone us-east1-b --tunnel-through-iap
chmod 600 ~/.kube/dsxa422.kubeconfig
#    then add this line under clusters[0].cluster, below "server:":
#      proxy-url: socks5://127.0.0.1:1080

# 2. Start the tunnel (leave it running)
gcloud compute ssh ocp-sno-admin --zone us-east1-b --tunnel-through-iap -- -N -D 127.0.0.1:1080 -o ServerAliveInterval=30

# 3. CLI tools
k9s --kubeconfig ~/.kube/dsxa422.kubeconfig
KUBECONFIG=~/.kube/dsxa422.kubeconfig kubectl get pods -n dsxa

# 4. Web console: open a separate Chrome instance that uses the tunnel
open -na "Google Chrome" --args --user-data-dir=/tmp/ocp-chrome --proxy-server="socks5://127.0.0.1:1080"
#    browse to https://console-openshift-console.apps.<cluster>.<baseDomain>
#    log in as kubeadmin (password: <install-dir>/auth/kubeadmin-password)

The console uses a self-signed certificate, so expect two warnings (console and OAuth). When you print the password with cat, a trailing % is the shell's no-newline marker, not part of the password.

12. Cleanup

To remove only the DSX/A application:

helm uninstall dsxa -n dsxa
oc delete project dsxa      # also removes the MongoDB PVC; Helm leaves StatefulSet volumes behind

To destroy the whole installer-provisioned cluster:

openshift-install destroy cluster --dir "$HOME/ocp-install/dsxa-gcp" --log-level=info

Afterwards, check the GCP project for orphaned disks, static IP addresses, DNS records, service accounts and registry resources. Don't delete the GCP project unless that's explicitly intended.

Removing a cluster whose install directory is lost

destroy needs the original directory. Without it, remove the cluster by hand. Every resource it created has the infra ID in its name or carries the label kubernetes-io-cluster-<infraID>=owned.

ID=<infraID>
for r in "compute instances" "compute disks" "compute instance-groups unmanaged" "compute forwarding-rules" \
         "compute target-pools" "compute target-tcp-proxies" "compute backend-services" "compute health-checks" \
         "compute firewall-rules" "compute addresses"; do
  gcloud $r list --filter="name~$ID" --format='value(name)'
done
gcloud dns managed-zones list | grep $ID
gcloud iam service-accounts list | grep $ID
gcloud storage ls | grep $ID

Delete in dependency order:

  1. VMs
  2. Forwarding rules
  3. Target TCP proxies and target pools
  4. Backend services
  5. Health checks and instance groups
  6. Addresses and firewall rules
  7. Public DNS records and the private zone
  8. Buckets and service accounts

The public API forwarding rule, backend service and health check are global; the internal ones are regional. Also remove the ingress load balancer the cluster's router created: a forwarding rule named a<hash> with the description openshift-ingress/router-default, its target pool and its k8s-fw- firewall rules.

Current automation gap

The repository provides the DSX/A Helm chart and deployment configuration, but not a single end-to-end script for:

  • GCP project and billing setup
  • GCP IAM and service accounts
  • VPC, subnet, firewall and DNS creation
  • OpenShift cluster creation
  • Registry credential provisioning
  • OpenShift project bootstrap
  • Post-deploy exposure (loadBalancerSourceRanges) and smoke tests (REST and ICAP)

For repeatable environment recreation, the recommended future structure is:

infrastructure/
  terraform/
    gcp-project/
    network/
    dns/
    openshift/
  openshift/
    project.yaml
    registry-secret-template.yaml
    values-gcp-ocp.yaml
    values-gcp-ocp-sno.yaml      # reduced resource requests for single-node clusters
    deploy-dsxa.sh
    smoke-test.sh                # REST /scan/binary/v2 and ICAP /response checks

Credentials, private keys, Red Hat pull secrets and DSX/A registration tokens must stay out of source control.
